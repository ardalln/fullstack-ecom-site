# KICKS — Go + PostgreSQL + React + JWT + OTP + Payments

بک‌اند و فرانت‌اند یک فروشگاه اینترنتی کتونی: ثبت‌نام/ورود با شماره موبایل و کد تایید (OTP)،
دفترچه آدرس، خرید محصولات با تراکنش دیتابیس، نمایش قیمت و تخفیف، و یک درگاه پرداخت آزمایشی.

## قابلیت‌های فروشگاه

- ورود OTP برای مشتری‌های موجود؛ نام، نام خانوادگی و نام کاربری فقط هنگام ساخت حساب جدید پرسیده می‌شود.
- تنوع‌های محصول با عنوان قابل‌تغییر (مثل سایز، رنگ یا حجم)، قیمت، موجودی و تصویر جداگانه.
- بنرهای جدا برای نمایشگر بزرگ و موبایل، روش‌های ارسال سراسری یا محدود به استان/شهر، کد تخفیف با سقف مصرف، و نشان «محبوب» برای اسلایدر صفحهٔ اصلی.
- هزینهٔ ارسال و تخفیف در بک‌اند محاسبه و هنگام ساخت سفارش ذخیره می‌شوند. هر سفارش کد پیگیری تصادفی دارد و وضعیت آن از مسیر `/api/v1/tracking/:code` قابل مشاهده است.
- فهرست نشانی، ۳۱ استان، ۱٬۲۵۳ شهر و ۴۲۹ شهرستان به صورت محلی بسته‌بندی شده است؛ منبع و مجوز داده‌ها در `frontend/src/data/SOURCES.md` ثبت شده است.

## پیش‌نیازها
- Go 1.23 یا بالاتر
- Node.js 20 یا بالاتر و npm (برای build یا توسعهٔ فرانت‌اند React)
- Docker (برای اجرای PostgreSQL) یا یک PostgreSQL نصب‌شده

## اجرا

اگر نسخه قبلی این پروژه را اجرا کرده‌اید، چون ساختار دیتابیس عوض شده (کاربران دیگر رمز
عبور ندارند، بلکه با شماره موبایل شناخته می‌شوند)، ابتدا volume قبلی را پاک کنید:

```bash
docker compose down -v   # فقط لازم اگر نسخه قبلی را اجرا کرده بودید
```

سپس:

```bash
cp .env.example .env          # مقادیر را در صورت نیاز تغییر بدهید
docker compose up -d          # اجرای PostgreSQL
go mod tidy                   # دانلود وابستگی‌ها (فقط بار اول)
npm --prefix frontend install # وابستگی‌های React (فقط بار اول)
npm --prefix frontend run build # ساخت فایل‌های فرانت‌اند که Go سرو می‌کند
go run ./cmd/api              # اجرای سرور روی http://localhost:8080
```

برای توسعهٔ زندهٔ React، در یک ترمینال API را اجرا کنید؛ در ترمینال دوم دستور
`npm --prefix frontend run dev` را بزنید و سایت را روی `http://localhost:5173` ببینید.
Vite مسیرهای API و تصویرهای بارگذاری‌شده را به سرور Go روی پورت ۸۰۸۰ می‌فرستد.

در PowerShell ویندوز، فایل `.env.example` را با نام `.env` در ریشهٔ همین پروژه کپی کنید؛
سپس `JWT_SECRET` را با یک مقدار تصادفی حداقل ۳۲ کاراکتری جایگزین کنید. برای ساخت مدیر اولیه،
`ADMIN_PHONE` را روی شمارهٔ موبایل خودتان بگذارید. تا زمان اتصال سرویس پیامک واقعی، کد ورود مدیر
در ترمینال سرور چاپ می‌شود.

## نکات امنیتی پیش از انتشار عمومی

- `.env.example` عمداً کلید JWT و شمارهٔ مدیر را خالی می‌گذارد؛ مقادیر قوی و متعلق به خودتان را تنظیم کنید.
- PostgreSQL در `docker-compose.yml` فقط روی `127.0.0.1` منتشر می‌شود تا از بیرون دستگاه در دسترس نباشد.
- مسیرهای پنل مدیریت در بک‌اند همگی JWT و نقش مدیر را بررسی می‌کنند؛ مخفی‌کردن لینک پنل به‌تنهایی مجوز دسترسی نیست.
- درخواست و بررسی OTP محدودیت نرخ دارند، هدرهای امنیتی روی پاسخ‌ها تنظیم شده‌اند و توکن پرداخت/کد پیگیری در لاگ سرور ماسک می‌شود.
- ارسال پیامک هنوز شبیه‌سازی‌شده است و کد OTP را در ترمینال چاپ می‌کند؛ درگاه پرداخت هم آزمایشی است. تا زمانی که ارائه‌دهندهٔ واقعی پیامک و پرداخت متصل نشده، پروژه را برای دریافت پول یا روی اینترنت عمومی منتشر نکنید.

هنگام شروع، migrationها خودکار اجرا می‌شوند (جدول‌ها + ۳ محصول نمونه + برند پیش‌فرض) و اگر `ADMIN_PHONE`
در `.env` تنظیم شده باشد، یک کاربر admin با آن شماره ساخته می‌شود (بدون رمز عبور؛ برای ورود
هم از همان مسیر OTP استفاده کنید).

## ساختار پروژه

```
cmd/api/main.go                 نقطه شروع، wiring و graceful shutdown
internal/config                 خواندن تنظیمات از env
internal/domain                 مدل‌ها، خطاها، اعتبارسنجی شماره موبایل و interfaceهای repository
internal/postgres                pool، migration، repositoryها و TxManager (pgx)
internal/service                منطق کسب‌وکار (auth/OTP, address, product, order, payment)
internal/auth                   ساخت و اعتبارسنجی JWT
internal/sms                    ارسال پیامک (فعلاً چاپ در ترمینال؛ قابل تعویض با یک سرویس واقعی)
internal/middleware              middleware احراز هویت و نقش (role)
internal/handler                هندلرهای Echo، DTOها، validator و error handler مرکزی
internal/router                 تعریف مسیرها و middlewareهای سراسری
frontend/src                    فرانت‌اند React، اجزا و سبک‌های فروشگاه کتونی
frontend/vite.config.js         build React به پوشهٔ داخلی frontend که Go embed می‌کند
internal/web/static             خروجی production ساخته‌شده با Vite و embedشده در باینری
```

جریان درخواست: `handler → service → repository (interface) → postgres`.

## ثبت‌نام و ورود با OTP

رمز عبور در این پروژه وجود ندارد. جریان کار دقیقاً شبیه فروشگاه‌های ایرانی واقعی
(دیجی‌کالا، اسنپ و مشابه) است:

1. `POST /api/v1/auth/otp/request` با `{ "phone": "09121234567" }` — یک کد ۶ رقمی
   ساخته می‌شود و «پیامک» می‌شود. چون سرویس پیامک واقعی متصل نیست، کد به‌صورت واضح در
   **ترمینالِ خودِ سرور** چاپ می‌شود (نگاه کنید به `internal/sms/sms.go`، `ConsoleSender`).
   محدودیت‌ها: کد تا `OTP_TTL` (پیش‌فرض ۲ دقیقه) معتبر است، بین دو درخواست باید
   `OTP_RESEND_COOLDOWN` (پیش‌فرض ۶۰ ثانیه) صبر کرد (در غیر این صورت خطای ۴۲۹)، و حداکثر
   `OTP_MAX_ATTEMPTS` (پیش‌فرض ۵) بار می‌توان کد اشتباه امتحان کرد.
2. `POST /api/v1/auth/otp/verify` با `{ "phone", "code" }`:
   - اگر شماره قبلاً ثبت‌نام کرده باشد، همان کاربر با یک JWT وارد می‌شود.
   - اگر شماره جدید باشد، باید `first_name` و `last_name` را هم در همین درخواست
     بفرستید (در غیر این صورت خطای ۴۲۲ با جزئیات فیلدهای لازم برمی‌گردد؛ کد هنوز مصرف
     نشده، پس می‌توانید با همان کد و نام کامل دوباره تلاش کنید). `email` اختیاری است.

برای وصل‌کردن یک سرویس پیامک واقعی (مثلاً Kavenegar، Ghasedak، ملی‌پیامک)، کافی است
`sms.Sender` را برای آن سرویس پیاده‌سازی کنید و در `cmd/api/main.go` به‌جای
`sms.NewConsoleSender()` بگذارید؛ بقیه کد بدون تغییر کار می‌کند.

## سبد خرید، آدرس و پرداخت — مثل یک فروشگاه واقعی

1. کاربر محصولات را به سبد اضافه می‌کند.
2. در پای صفحه سبد، یکی از آدرس‌های ذخیره‌شده را برای ارسال انتخاب می‌کند (اگر آدرسی
   ندارد، لینک «افزودن آدرس» را می‌بیند).
3. با زدن «ثبت سفارش»، ابتدا `POST /orders` صدا زده می‌شود (سفارش با وضعیت
   `awaiting_payment` ساخته و موجودی محصولات کم می‌شود)، سپس `POST /orders/:id/pay`
   یک `authority` می‌سازد و کاربر به صفحه‌ی «درگاه پرداخت» (شبیه‌سازی‌شده، مدل‌گرفته از
   جریان کار زرین‌پال) هدایت می‌شود.
4. در آن صفحه با زدن «پرداخت» سفارش `paid` می‌شود و یک کد پیگیری (ref id) صادر می‌شود؛
   با زدن «انصراف از خرید» سفارش `cancelled` می‌شود و موجودی محصولات به فروشگاه
   برمی‌گردد. یک سفارشِ لغوشده نهایی است — برای خرید دوباره باید سفارش تازه ثبت شود.

برای وصل‌کردن یک درگاه واقعی (زرین‌پال، آیدی‌پی و مشابه)، `internal/service/payment.go`
نقطه شروع است: به‌جای ساختن `authority` محلی، باید API «درخواست پرداخت» درگاه را صدا
بزنید و کاربر را به URL برگشتی آن هدایت کنید؛ endpoint تایید هم به‌جای گرفتن اکشن از
کاربر، callback درگاه را می‌گیرد و API «تایید تراکنش» آن را صدا می‌زند.

## پنل مدیریت

پس از ورود با شمارهٔ تنظیم‌شده در `ADMIN_PHONE`، نشانی `/admin` را مستقیماً در مرورگر باز کنید. پنل فارسی و
راست‌چین با سایدبار سمت راست، نمای کلی فروشگاه، ساخت/ویرایش/حذف و فعال یا غیرفعال‌کردن محصول، انتخاب روشن دستهٔ اصلی یا زیر‌دسته، مدیریت برند،
گالری تصویر، ویژگی‌ها، قیمت تخفیفی، تنوع‌های محصول و مدیریت تأیید دیدگاه‌ها را دارد. برای تنوع‌ها می‌توان عنوانی مثل رنگ، سایز، ظرفیت یا حجم
وارد کرد؛ هر گزینه مقدار، قیمت، موجودی و تصویر جداگانه دارد. انتخاب تنوع، قیمت و موجودی همان گزینه را در صفحهٔ محصول نشان می‌دهد،
و تصویر اختصاصی آن را نمایش می‌دهد یا در نبود آن به تصویر اصلی برمی‌گردد. سفارش شناسه و مشخصات تنوع و قیمت زمان خرید را ثبت می‌کند.
قیمت کلی در فهرست، کمترین قیمت تنوع و موجودی کلی، مجموع موجودی تنوع‌ها است. منوی «محصولات» در سربرگ دسته‌های اصلی و
زیر‌دسته‌ها را نشان می‌دهد و صفحهٔ محصول مسیر دستهٔ اصلی/زیر‌دسته را کنار تصویر نمایش می‌دهد.
محصول غیرفعال در فهرست و صفحهٔ عمومی فروشگاه نمایش داده نمی‌شود و امکان ثبت سفارش آن نیز وجود ندارد. صفحهٔ محصول عکس اصلی را
در ابتدا نشان می‌دهد؛ تصاویر گالری به‌صورت بندانگشتی قابل انتخاب‌اند و تصویر اختصاصی تنوع پس از انتخاب همان تنوع نمایش داده می‌شود.
در ادامهٔ صفحهٔ محصول، تا شش محصول فعال از همان دسته یا برند پیشنهاد می‌شود.
برای کالای ساده می‌توان قیمت تخفیفی وارد کرد؛ درصد تخفیف از اختلاف قیمت عادی و تخفیفی محاسبه می‌شود و checkout هم همان مبلغ تخفیف‌خورده را ثبت می‌کند. برای کالای متغیر، هر سایز قیمت عادی و تخفیفی مستقل دارد.
محصولات نمونهٔ اولیه در migration جدید فقط در صورتی که هنوز نام آزمایشی اولیه را داشته باشند به کتونی نمونه تبدیل می‌شوند.
تصاویر روی دیسک در پوشهٔ `uploads/` ذخیره می‌شوند. جست‌وجوی کاربران و تغییر نقش یا وضعیت حساب
هم در پنل موجود است. مدیر فعلی نمی‌تواند دسترسی خودش را تغییر دهد و
سامانه اجازهٔ غیرفعال‌کردن آخرین مدیر فعال را نمی‌دهد. تغییر دسترسی در درخواست بعدی اثر می‌کند،
حتی اگر کاربر JWT قبلی داشته باشد.

در استقرار روی سرور یا کانتینر، برای پوشهٔ `uploads/` فضای ذخیره‌سازی پایدار در نظر بگیرید؛
فایل‌های تصویر باید همراه دیتابیس پشتیبان‌گیری شوند.

## پنل کاربری، وبلاگ و پشتیبانی

پس از ورود، با انتخاب نام کاربر در سربرگ وارد `#/account` شوید. پنل کاربری اطلاعات حساب، سفارش‌های من، آدرس‌های من و
گفت‌وگوهای پشتیبانی را یکجا در اختیار کاربر می‌گذارد. کاربر می‌تواند تیکت بسازد و پیام‌های بعدی را در همان گفت‌وگو بفرستد؛
مدیر از `/admin/tickets` تیکت‌ها را می‌بیند، پاسخ می‌دهد و وضعیت را تغییر می‌دهد. تیکت بسته‌شده قابل پاسخ نیست.

مدیر از `/admin/blog` مطلب وبلاگ را با عنوان، اسلاگ، خلاصه، متن، تصویر کاور و metadata سئو می‌سازد و منتشر یا پیش‌نویس می‌کند.
صفحه‌های `/blog` و `/blog/:slug` در سرور رندر می‌شوند تا متن مطلب و metadata اصلی در HTML اولیه در دسترس خزنده‌های موتور جست‌وجو باشد.

مدیریت سفارش از انتقال‌های مرحله‌ای استفاده می‌کند: سفارش پرداخت‌نشده را می‌توان لغو کرد و موجودی
آن به‌صورت تراکنشی برمی‌گردد؛ سفارش پرداخت‌شده از «در حال آماده‌سازی» به «ارسال‌شده» می‌رود و
«ارسال‌شده» آخرین وضعیت است. در مهاجرت پایگاه داده، سفارش‌های قدیمی «تحویل‌شده» به «ارسال‌شده»
منتقل می‌شوند. لغو یا بازپرداخت سفارش پرداخت‌شده نیازمند اتصال درگاه واقعی و فرایند بازپرداخت است.

## تراکنش خرید

`OrderService.PlaceOrder` همه‌چیز را در **یک تراکنش** انجام می‌دهد: قفل ردیف محصولات
(`SELECT ... FOR UPDATE`، به ترتیب id تا deadlock پیش نیاید)، بررسی موجودی، کم‌کردن
موجودی، و ساخت سفارش با یک snapshot از آدرس انتخاب‌شده (نام، شماره تماس، استان، شهر،
آدرس، کدپستی) — تا ویرایش یا حذف بعدی آن آدرس، آدرس ثبت‌شده روی سفارش‌های قبلی را
تغییر ندهد. لغو پرداخت هم در یک تراکنش، وضعیت سفارش را عوض و موجودی را برمی‌گرداند.

## تست با Postman

فایل `docs/shop-api.postman_collection.json` را Import کنید (Import ← Upload Files) و
پوشه‌ها را به ترتیب اجرا کنید: `1. Auth (OTP)` → `2. Addresses` → `3. Products` →
`4. Orders & Payment` → `5. Negative cases`.

**نکته مهم:** چون کد تایید واقعاً پیامک نمی‌شود، باید بعد از اجرای درخواست
«Request OTP»، به **ترمینالی که `go run ./cmd/api` در آن اجرا شده** نگاه کنید و کد
۶ رقمی چاپ‌شده را در متغیر کالکشن `otp_code` (یا مستقیم در بدنه درخواست بعدی) بگذارید،
سپس «Verify OTP» را بزنید. توکن‌ها و شناسه‌های دیگر (سفارش، آدرس، authority پرداخت)
خودکار در متغیرهای کالکشن ذخیره می‌شوند.

## نکات

- قیمت‌ها عدد صحیح و بر حسب کوچک‌ترین واحد پول هستند (بدون float).
- `JWT_SECRET` باید حداقل ۳۲ کاراکتر باشد. برای production حتماً مقدار تصادفی جدید بسازید
  (`openssl rand -hex 32`).
- شماره موبایل هم برای ثبت‌نام و هم برای آدرس گیرنده باید فرمت موبایل ایران باشد
  (`09xxxxxxxxx`؛ ورودی‌های `+98`, `0098`, `98` هم به همین شکل نرمال می‌شوند).
- کدپستی باید دقیقاً ۱۰ رقم باشد.
- نقش اولیه داخل JWT ذخیره می‌شود، اما middleware برای هر درخواست نقش و فعال‌بودن حساب را از
  دیتابیس می‌خواند؛ بنابراین تغییر دسترسی با توکن قبلی هم در درخواست بعدی اعمال می‌شود.

## چیزهایی که پیاده‌سازی نشده (خارج از این نسخه)

- اتصال واقعی به یک سرویس پیامک یا درگاه پرداخت (هر دو mock/شبیه‌سازی‌شده‌اند، اما
  معماری برای جایگزینی آسان طراحی شده — بالاتر توضیح داده شد).
- Refresh token (فقط access token با TTL قابل‌تنظیم).
- تست خودکار Go (چون repositoryها interface هستند، برای mock کردن در unit test آماده‌اند).
